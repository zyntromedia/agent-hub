# 🛠️ Pull Request Workflow Agent

## 🎯 หน้าที่
- สร้างคำอธิบาย PR จาก Diff และประวัติ Commit อัตโนมัติ
- ตรวจสอบให้ตรงตามเกณฑ์ก่อน Review
- ตรวจสอบรูปแบบ Commit (Conventional Commits)
- ตรวจสอบ CI/CD, ความปลอดภัย, และเอกสารประกอบ
- แจ้งให้ครบถ้วนก่อนส่งให้ผู้ตรวจสอบ

## 📋 เกณฑ์การตรวจสอบ

### ✅ ขั้นตอนที่ 1 — ข้อมูล PR ครบถ้วน
- [ ] มีชื่อ PR ตามรูปแบบ: `type: brief description`
- [ ] มีคำอธิบายการเปลี่ยนแปลงที่ชัดเจน
- [ ] มี Issue ที่เกี่ยวข้อง (ถ้ามี)
- [ ] มีพื้นที่เปลี่ยนแปลง: ความสามารถที่เพิ่ม/แก้ไข, การทดสอบ

### ✅ ขั้นตอนที่ 2 — คุณภาพโค้ด
- [ ] Commit ตามรูปแบบ Conventional Commits
- [ ] CI/CD ทั้งหมดผ่าน ✅
- [ ] ไม่มี Secrets หรือข้อมูลละเอียดอ่อน
- [ ] อัปเดตเอกสาร (README, docs/) ตามความจำเป็น
- [ ] เพิ่มการทดสอบ (ถ้ามีฟีเจอร์ใหม่)

### ✅ ขั้นตอนที่ 3 — ความปลอดภัยและมาตรฐาน
- [ ] ตรวจสอบ `.env*` ไม่ได้คอมมิตลงแหล่งที่มา
- [ ] ตรวจสอบการเปลี่ยนแปลงในไฟล์ที่ละเอียดอ่อน:
  - `SECURITY.md`, `CODEOWNERS`, `.github/workflows/`
- [ ] ไม่มี Dependency ที่มีความเสี่ยง

## 🔀 กฎสาขา
- `main` ← รับจาก `develop` หรือ Hotfix เท่านั้น
- `develop` ← รับจากสาขา `feature/*`, `fix/*`, `docs/*`
- สาขา Feature: ลงท้ายด้วยชื่อฟีเจอร์ เช่น `feature/ai-caption`

## 📝 รูปแบบชื่อ PR
- `feat: …` — ฟีเจอร์ใหม่
- `fix: …` — แก้ไขบั๊ก
- `docs: …` — อัปเดตเอกสาร
- `refactor: …` — ปรับโครงสร้างโค้ด
- `perf: …` — ปรับปรุงประสิทธิภาพ
- `ci: …` — ปรับปรุง CI/CD
- `chore: …` — งานทั่วไป (แก้ไขโค้ดไม่มีผลต่อการทำงาน)

## 🚀 ขั้นตอนการทำงานของ Agent
1. อ่าน Diff และประวัติ Commit → สร้าง/เติมคำอธิบาย PR
2. ตรวจสอบเกณฑ์ตาม Checklist ด้านบน
3. ตรวจสอบรูปแบบ Commit ด้วย `scripts/check-commit-messages.sh`
4. ตรวจสอบ CI Status และผลการตรวจสอบจาก CodeRabbit
5. ถ้าผ่านทั้งหมด → แจ้งว่า **พร้อมสำหรับการตรวจสอบ** ✅
6. ถ้ายังไม่ผ่าน → แจ้งรายการที่ต้องแก้ไข พร้อมคำแนะนำ

## 📌 เมื่อพบปัญหาในไฟล์สำคัญ
ถ้ามีการแก้ไขไฟล์กลุ่มนี้ → ต้องแจ้งให้ผู้ดูแลระบบทราบ:
- `.github/workflows/`
- `.coderabbit.yaml`
- `SECURITY.md`
- `CODEOWNERS`
- `docker-compose.yml`, `Dockerfile`
- `.env.example`
